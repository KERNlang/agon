# ARGUMENT: THIS PLAN WILL PRODUCE FALSE GREENS — ACCEPTANCE IS PREMATURE

## I. THE FOUNDATION IS COMPROMISED BEFORE TESTING BEGINS

### A. "Clean Compilation" Is a Lie Disguised as Evidence

The plan cites S1B clean evidence as the entry gate. But the diff itself reveals the foundation is poisoned: **clean staged compilation fails without ignored declarations**. This is not a minor tooling artifact. It means TypeScript's own type checking — the mechanism that guarantees module boundaries are respected — has been disabled for some set of files to make the build pass.

When a modularization plan cannot pass compilation without `exclude` masks or `skipLibCheck` workarounds that sweep real errors under the rug, the modularization has not been validated. The "clean evidence" in S1B proves only that a compromised build can pass a compromised test. It does not prove that the module graph is coherent.

Specifically: `tsconfig.json` exclusions in a modular TypeScript project are a code smell. They typically indicate either (a) unconverted legacy `.js`/`.d.ts` files that haven't been ported to the new module system, or (b) circular dependencies that `tsc` would catch and reject if the exclusions weren't hiding them. Either way, this is an external blocker. No amount of S2–S9 testing can compensate for a build system that is lying about type safety.

### B. Hashes Against Ambient Files Are a Security Hollow Point

The plan states **hashes used ambient files** as a corrected fact from the superseded green receipt. This is not a mere bookkeeping fix. It is a fundamental security regression.

When dependency integrity is verified against `.d.ts` files rather than `.js`/`.mjs` implementation files, the following attack vector opens: a malicious package can ship a benign type declaration (passing hash verification) while the runtime implementation contains exploit code. The hash check will pass because the ambient declaration matched the recorded hash — but the runtime code was never verified.

This is especially dangerous in the context of S8 (trust/grants/folder mods) and S9 (third-party integration), where external packages are being integrated. Without hash verification against actual binary payload, "fail-closed" third-party behavior (S7) has no cryptographic foundation.

**External blocker**: Dependency hashes must be computed over the actual published artifact (`files`/`dist` payload), not the ambient declaration package. This requires coordination with the package registry tooling (npm/pnpm/yarn) to extract and verify post-publish.

### C. 148 Entries With 4 Duplicates Reveals Unaudited Dependency Graph

148 entries is a large dependency graph. Four duplicates in that graph — before modularization — means the dependency resolution was not deterministic before slicing. When you cut 852 legacy source assignments across a graph that was not deterministically resolved, you are distributing non-determinism. The topological ordering mentioned in the plan (49 packages, 144 unique edges) may be correct for the corrected graph, but **the 852 legacy source assignments were made against the uncorrected graph**.

Each of those 852 assignments maps a legacy source file to a target package. If the target package boundaries shifted when the duplicate dependencies were resolved, some of those 852 assignments may now point to the wrong package. There is no evidence in this plan that the 852 assignments were re-validated after the duplicate correction.

## II. S7 TRANSACTIONAL GUARANTEES ARE ASSERTED, NOT VERIFIED

### A. Concurrent-Writer Is Not Tested — It Is Named

S7 explicitly calls out "concurrent-writer" testing. This is the hardest problem in transactional systems. The plan lists it as a test category but provides no specification of what "concurrent-writer safety" means in this system:

- What locking granularity? File-level? Package-level? Registry-level?
- What happens when two `agon` processes race to update the same config file simultaneously?
- What is the consistency model? Linearizable? Sequential? Eventual?

Without answers, "concurrent-writer tests" is a feature name, not evidence. The most common failure mode in concurrent file system writes — the torn-write — requires formal specification of what constitutes an atomic commit before it can be tested.

### B. ENOSPC/EACCES Are Named But Not Specified

S7 mentions ENOSPC (disk full) and EACCES (permission denied) tests. These are system-call-level failures. The question is: what is the **recovery behavior**? Does the transaction roll back? Does it retry? Does it leave the system in a half-applied state?

A fail-closed third-party strategy (also in S7) that doesn't define ENOSPC behavior has a critical gap: if disk is full during a package write, and the system doesn't detect this, it will silently proceed as if the write succeeded — producing an inconsistent state that will fail at the next boot.

**Local fix**: Define explicit error codes for ENOSPC and EACCES in the transactional state machine, with mandatory rollback triggers on each.

**External blocker**: ENOSPC recovery requires coordination with the host OS filesystem layer and the package manager's on-disk state — both of which are external to the CLI.

### C. Torn-Write Detection Requires Formalization

Torn-write (when a write is interrupted mid-byte, leaving a partial file) is mentioned in S7 but not defined. The mitigation for torn-writes is typically atomic rename (write to temp, then rename), but this requires:

1. The filesystem supports atomic rename (not all do — network filesystems, some containers)
2. The transaction log records the rename as the commit point, not the write
3. Crash recovery replays from the transaction log

None of this is specified. Torn-write tests without this context produce false negatives — the tests may pass on a local ext4 filesystem and fail silently on a Docker volume or NFS mount.

## III. CROSS-PLATFORM CONCERNS ARE TREATED AS ONE PROBLEM

### A. npm/npx, macOS Native, Linux Native Have Conflicting Security Models

S9 bundles npm/npx, native macOS, native Linux, and historical state migration into one slice. These four surfaces have fundamentally different security and failure models:

- **npm/npx**: Runs in userspace, respects npm's global/local prefix, dependency resolution is npm's job. Failures are scoped to the npm process tree.
- **macOS native**: May involve `.pkg`/Homebrew, requires sudo for system paths, and interacts with macOS Gatekeeper and notarization requirements. ENOSPC on `/Applications` has different semantics than on npm prefix.
- **Linux native**: May involve `/usr/local/bin`, systemd integration, and Linux permission models (setuid binaries, SELinux/AppArmor contexts). EACCES on `/usr/local` requires root escalation.

The plan provides a single slice for all four. This means either (a) the behavioral differences have been abstracted away — which is a massive assumption, or (b) the abstraction layer itself is untested.

**Critical gap**: The macOS notarization and Linux systemd integration paths are not mentioned. If the modularization produces binaries that need system-level installation, the macOS binary must be notarized. If it ships as a Linux systemd unit, that unit has its own failure modes. Neither is addressed.

### B. Historical State Migration (S9) on Live Systems

Migrating historical state is dangerous on live systems because the migration must not lose data in flight. If a user has an `agon` process running while S9 migration runs, the migration may read inconsistent state. There is no mention of:

- Process isolation during migration (stop the daemon first?)
- Version detection (which historical format is being migrated from?)
- Rollback if migration corrupts the historical state

852 legacy source assignments suggest a rich historical state. Migrating this under load is a production-critical concern.

## IV. S8 TRUST/GRANTS SECURITY MODEL IS UNSPECIFIED

### A. No Threat Model

S8 introduces trust/grants/folder mods with "fail-closed" as the stated security posture. But fail-closed against what threat? The plan does not specify:

- **Trusted by whom?** Is the trust origin the host system, the user, the package registry, or the module itself?
- **Grants to whom?** Do mods have capability tokens? Are they signed?
- **What is the attack surface?** Malicious mod injection via filesystem? Via npm? Via a compromised config file?

Without a threat model, "fail-closed" is a marketing claim. In one scenario, fail-closed means "reject unknown packages." In another, it means "deny all capability requests by default." These produce very different user experiences and security properties.

### B. Folder Mods Without ACL Specification

"Folder mods" implies mods scoped to specific directories. But what happens when two mods have overlapping folder scopes? Does the most restrictive win? The most recent? Is there a priority ordering? Without an Access Control List (ACL) specification for folder boundaries, mods can bleed across their intended isolation boundaries.

## V. N-1/N-2 COMPATIBILITY IS VAGUE AND UNTESTED

### A. What Does N-2 Mean for a CLI Tool?

The plan claims N-1/N-2 compatibility across eleven support packages (S4). For a CLI tool, "N-2 compatibility" is ambiguous:

- Does it mean Node.js N-2? (Current LTS is Node 22, so N-2 = Node 20. Is Node 20 tested?)
- Does it mean the tool must run on Node 20?
- Does it mean the tool's output format must be compatible with Node 20 behavior?

Node 20 reaches End of Life in April 2026. If this modularization ships in 2025, N-2 means supporting Node 18 (EOL October 2025). These are moving targets with hard deadlines.

### B. Type Baseline Against Which Node Version?

S4 mentions "type baseline." TypeScript type definitions for Node.js vary by version. If the type baseline targets Node 20, and Node 22 introduces new types, the modularization must either (a) drop support for Node 20 and update the type baseline, or (b) maintain dual type baselines. Neither is specified.

The phrase "has rollback" is not evidence of correctness. It is a feature claim.

## IX. PRIORITIZED VERDICT

### External Blockers (Require Coordination Beyond This Repo)

1. **Remove all tsconfig exclusions and `skipLibCheck` workarounds.** Compilation must pass `tsc --strict` without ignores. This requires actual modularization of the ambient files, not exclusion. The superseded green receipt was right to flag this.

2. **Recompute dependency hashes over artifact payloads, not ambient declarations.** This requires coordination with the package registry pipeline to verify the post-publish artifact against the pre-publish hash.

3. **Audit 852 legacy source assignments against the corrected dependency graph.** Verify each assignment maps to the correct target package post-duplicate-resolution.

4. **Specify macOS notarization and Linux systemd integration paths.** These are regulatory and OS-integration requirements that cannot be tested in isolation.

5. **Define the N-1/N-2 Node.js compatibility horizon with hard EOL dates.** Compatibility is not free; every supported version multiplies test matrix and CI cost.

### Locally Actionable Fixes

1. **Formalize the transactional state machine** for S7 with explicit error codes, state transitions, and rollback triggers. Document ENOSPC and EACCES behavior formally before writing tests.

2. **Define the concurrent-writer consistency model** — linearizable, sequential, or eventual — and specify the locking strategy. Write the test specification before writing the tests.

3. **Produce a threat model for S8** before implementing trust/grants. Define what "fail-closed" means operationally: what is rejected, by whom, under what conditions, and with what user-visible error?

4. **Specify the disable matrix coverage target** (e.g., all-pairs at minimum) and produce the conflict exclusion list before declaring the matrix tested.

5. **Test rollback under adversarial conditions**: disk full during rollback, concurrent access during rollback, partial-step failure during multi-surface update (S6).

## FINAL ASSESSMENT

This plan has the correct **vocabulary** of a modularization acceptance document — it names slices, edges, rollback, transactions, and security posture. But vocabulary is not evidence. The plan cannot demonstrate that the module graph is type-safe (compilation compromised), that the security model is enforceable (hash hollow point), or that the transactional system is correct (concurrent-writer unspecified). These are not gaps that more testing will reveal — they are gaps that invalidate the testing framework itself.

**Do not accept this plan.** It will produce a green receipt for a build that is not clean, a dependency graph that has not been audited, and a security model that has not been specified. The next green receipt will be just as false as the one it supersedes.
