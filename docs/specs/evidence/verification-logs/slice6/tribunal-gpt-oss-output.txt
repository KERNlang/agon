**Red‑team findings – concrete defects uncovered in the current cut‑over**

| # | Defect | Concrete evidence | Why it’s a defect |
|---|--------|-------------------|-------------------|
| 1 | **False‑green (tools reported as available but actually disabled)** | `packages/cli/src/cesar/tools.ts` – `register` only registers a handler if `<handler.definition.name>` is *both* in `CESAR_SURFACE_IDS` *and* in the explicit `available` set. `CESAR_SURFACE_IDS` is built from `FIRST_PARTY_SURFACE_CATALOG.filter(...).map(...).` If the catalog contains an alias that is not a primary `publicId`, the alias will never be matched by `handler.definition.name` and the tool will be omitted even though the surface is “enabled” in the catalog.  <br>Line numbers: 24–32 in the changed file. | A tool appears “enabled” (because the catalog claims it) but a user cannot invoke it – this is a false‑green. |
| 2 | **Disabled‑reachability (some CLI sub‑commands become unreachable after the surface cut‑over)** | `packages/cli/src/lazy-commands.ts` – `createGeneratedLazySubCommands` filters `legacyLazyCommandImplementations` via `<available.has(meta.name)>`. The default `available` is `processSurfacePublicIds('cli')` which is derived from the catalog; however, if a surface’s *publicId* has a leading slash while the command meta uses a non‑slashed name (or vice‑versa), the comparison fails.  <br>Lines 27–36 and 49–54 in the diff. | Certain commands such as `/agent-guide` may technically exist in the catalog but the lazy loader can no longer find them, making them unreachable. |
| 3 | **Lifecycle disposal leak for committed registry entries** | `packages/mod-kernel/src/registry.ts` – After the call to `stage`, the commit logic installs `entry.committedDispose = this.#register(...)` but still keeps the `ownedDisposers` array that calls the disposable at the end of the transaction. This means `entry.committedDispose` will *never* be executed on a normal commit path (the loop that calls disposers is only fired on an exception or rollback).  <br>Lines 169–174 and 189–199 in the changed file. | After a successful commit, resources that were registered and that need to be cleaned up when the registry closes are never disposed – a lifecycle memory leak. |
| 4 | **Generation atomicity failure for MCP tools** | `packages/mcp/src/agon-orchestration.ts` – `listMcpTools` now filters by `MCP_SURFACE_METADATA.has(tool.name)` *and* `available.has(tool.name)`. The `MCP_SURFACE_METADATA` map is built only from entries in the catalog with `category === 'mcpTools'`. If the catalog contains a *different* surface id that should be mapped to the same MCP tool name, the tool will be omitted from the list, breaking the atomicity of surface generation. <br>Lines 453–459 and 470 in the diff. | The list of available MCP tools may change inconsistently between catalog generations, breaking client expectations of a stable set of tools. |
| 5 | **Physical‑package activation bug (packages are not closed when missing)** | `packages/mcp/src/agon-orchestration.ts` – In `startMcpServer`, when a tool name is received from the client, there is a check if the name is in `MCP_SURFACE_METADATA`. If it isn’t, the server replies with `-32602` (“Unknown or disabled tool”). However, it *does not* close the connection or fail the process – the client may resume and attempt to call the same tool again, never receiving a definitive “closed” state. <br>Lines 476–483. | Clients that receive a “tool missing” error are left in a stale state; a retry will always fail, but the user is not reminded that the package is missing. |
| 6 | **Alias collision between tool registry and CLI commands** | `packages/cli/src/cesar/tools.ts` and `packages/cli/src/lazy-commands.ts` both register commands/tools by name. `createCesarToolRegistry` registers only if `handler.definition.name` is in `CESAR_SURFACE_IDS`. If a tool’s `publicId` accidentally collides with a CLI sub‑command name (e.g. `/agent` vs `agent`), the command can be overridden and hidden. The collision logic is not checked anywhere. <br>Lines 18–21 and 25–32. | Users may invoke a command that silently triggers a different tool, or vice versa; this is an alias collision. |
| 7 | **Documentation projection missing required docs file** | `scripts/generate-mode-docs.mjs` – The script parses the generated surface catalog and fails if an entry with `publicId === 'docs/modes.md'` is *not* in the `docs` surface projection. If the catalog or the environment is mis‑configured, the script will crash. <br>Lines 18–32 of the diff. | The documentation generation relies on a missing entry; the docs build will silently break. |
| 8 | **Rollback/ re‑entry failure after a registry transaction** | `packages/mod-kernel/src/registry.ts` – On rollback, the code iterates over `ownedDisposers` and calls each. However, it does **not** clear the `registeredDeclarations` set for entries that were registered *before* the rollback, because those declarations were removed only when the disposable was called, but the entry’s `deleted` flag is not cleared. This can lead to state inconsistency after multiple rollbacks and re‑entries. <br>Lines 196–208. | Uncommitted registrations can linger, causing subsequent operations to behave unpredictably. |
| 9 | **Compatibility‑authority error when checking surface availability** | The new `assertProcessSurfaceAvailable('cli', meta.name)` in `packages/cli/src/lazy-commands.ts` assumes that the `meta.name` of a command exactly matches the catalog surface id. However, commands may be aliased (e.g. `agent-guide` vs `agentGuide`) and the check uses the raw `meta.name`. If the catalog uses a different casing or alias, the assertion fails and the command aborts. <br>Lines 30–33 and 41–42. | A command that should be globally available fails because the authority check mis‑identifies it, breaking compatibility. |

---

### Bottom‑line

The current surface cut‑over introduces multiple concrete defects:

* **False‑green** – enabled surfaces that are not actually available in the registry.
* **Disabled‑reachability** – commands that cannot be invoked after the surface filter.
* **Lifecycle disposal leaks** – committed registry entries that are never disposed.
* **Generation atomicity** – MCP tool set that changes inconsistently between generations.
* **Physical‑package activation** – missing packages leave clients dangling instead of closing.
* **Alias collision** – tool names and CLI command names accidentally collide.
* **Docs** – the generation script can crash if a required docs surface is missing.
* **Rollback / re‑entry** – state can become inconsistent after transactions.
* **Compatibility‑authority** – commands may fail due to mismatched surface id checks.

These issues need to be addressed before the new surface infrastructure can be considered safe for production.
