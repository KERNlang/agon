**Defect #1: CLI surface generation fails to include 36 physical user mods—missing packages fail closed.**
OPEN — `createGeneratedLazySubCommands` in `lazy-commands.ts` filters `legacyLazyCommandImplementations` using only `processSurfacePublicIds('cli')`, which sources from `FIRST_PARTY_SURFACE_CATALOG`. The diff shows no evidence that *third-party* or *user-mod* packages are integrated (e.g., no `getLocalSurfaceCatalog` call, no `--mods` flag, no config fallback), yet `modular-agon-current-inventory.json` lists 36+ distinct mod packages (e.g., `mod-browser`, `mod-rag`, `mod-rooms`). There is no code to *dynamically* discover or validate them at runtime, and no `assertProcessSurfaceAvailable`-style guard for unknown mod IDs. A user enabling a non-first-party mod via `--mod=mod-rag` will hit runtime `Unknown command` (not “fail closed”), because `lazySubCommands` is fully precomputed at import time.

**Defect #2: Cesar tool registry is logically disabled for custom/mixed workloads.**
OPEN — `createCesarToolRegistry` in `tools.ts` hardcodes `CESAR_SURFACE_IDS` from `FIRST_PARTY_SURFACE_CATALOG` *and* accepts `available` as a parameter, but nowhere does `citty` invoke `createCesarToolRegistry` with a user-mod-inclusive set. If a user runs `/agent –mod=mod-rag`, Cesar’s `ToolRegistry` will omit `rag`-specific tools (which aren’t in `FIRST_PARTY_SURFACE_CATALOG`), even though `mod-rag` may register a custom tool handler. The `assertOpen` block in the diff *adds* a conditional guard, but the `filter((entry) => entry.category === 'cesarTools')` in `CESAR_SURFACE_IDS` construction excludes all non-`cesarTools` mods, so any mod not explicitly tagged as such is silently dropped.

**Defect #3: Alias-collision and disabled-reachability in `/help`.**
OPEN — `createSlashCommands` filters by `category === 'tuiSlashCommands'` *and* filters `available: ReadonlySet<string>`. But `SLASH_COMMANDS` is exported *without* `available` (final line: `createSlashCommands()`). In `detectIntent`, the call `parseSlashCommand(input, commandRegistry, available)` receives `available`, but CLI `/help` renders `SLASH_COMMANDS` *statically*, so users see *all* commands (including disabled) while the intent parser rejects them. This creates a green/docs mismatch: `agon --help` lists `/team-tribunal` (visible) but `agon /team-tribunal` errors “Unknown slash command”.

**Defect #4: MCP tool list does not gate lifecycle disposal or rollback.**
OPEN — `listMcpTools` in `agon-orchestration.ts` filters by `MCP_SURFACE_METADATA.keys()`, but the `MCP_SURFACE_METADATA` map is built *once* from `FIRST_PARTY_SURFACE_CATALOG`; there is no binding to `ModRegistry#committed` state. If a mod is disabled during a session (e.g., via `/config user-toggleable-mods = []`), the MCP server continues advertising disabled tools until restart. Worse, the `tools/call` guard `if (!MCP_SURFACE_METADATA.has(toolName))` uses *compile-time* metadata, not a per-session runtime registry—so a disabled tool triggers `Unknown or disabled tool`, but the API client cannot distinguish “never supported” vs “disabled now”, and no rollback/migration path is provided.

**Defect #5: Physical-package activation does not enforce atomicity or rollback integrity.**
CONCRETE — In `registry.ts`, the `ownedDisposers` are collected *before* `#register` succeeds for each staged entry. If `#register` throws during commit (e.g., mod `mod-rag`’s `manifest.install` hook fails), the `catch` block calls `dispose()` in reverse order, but `entry.committedDispose` is only assigned *after* `#register`. In the error path, `await entry.committedDispose?.()` will be `undefined`, so disposers registered *during* `staged` iteration are *not* rolled back, leaving partial state (e.g., partial file copy or registry entry). This breaks generation atomicity: 36 mods install, 1 fails, 35 remain inconsistently configured.

**Defect #6: docs generation assumes `docs/modes.md`—no fallback on missing or stale catalog entries.**
CONCRETE — `generate-mode-docs.mjs` *enforces* `docs/modes.md` exists in the catalog via `.filter…some((entry) => entry.publicId === 'docs/modes.md')` but offers *no* fallback. If the user’s surface catalog (e.g., from a custom `--pack`) omits `docs/modes.md`, the process throws “docs/modes.md is disabled or absent” and exits *non-zero* without generating *any* docs. In contrast, the CLI should emit partial docs (e.g., `modes.md + other/docs/*`) and warn. Additionally, the script hardcodes `packages/cli/dist/index.js`—no environment override for CI or containerized builds, meaning `AGON_DOCS_CLI_PATH` is unused in practice.

**Defect #7: CLI `assertProcessSurfaceAvailable` is inserted too late to catch invalid module activation.**
CONCRETE — `lazyCommand` wraps `resolve()` *and then* calls `assertProcessSurfaceAvailable('cli', String(meta.name))`. This means if `meta.name` is `mod-rag/unknown-subcommand`, `resolve()` imports the module *before* checking availability. A stale client with `mod-rag` uninstalled still triggers `import('./commands/mod-rag/unknown-subcommand.js')`, causing `ENOTFOUND` or `MODULE_NOT_FOUND` *after* the module’s `package.json` is loaded but *before* guard hits `assertProcessSurfaceAvailable`. The correct insertion point would be *before* `resolve()`.

**Defect #8: Surface-authority and intent parsing diverge on category-based inclusion.**
CONCRETE — `createTuiSurfaceIds` includes `tuiSlashCommands`, `intentVariants`, and `builtinCommandMetadata`, but `createSlashCommands` only filters `tuiSlashCommands`. This means an alias like `/team-brainstorm` defined as an `intentVariant` appears in `createTuiSurfaceIds` (and thus `available` in `detectIntent`) but is *not* rendered in `SLASH_COMMANDS` or `/help`. A user can invoke `/team-brainstorm` via intent parsing but cannot *discover* it from documentation, violating docs and physical-package activation coherence.

**Defect #9: Missing rollback RE-entry safety for disabled mods.**
OPEN — No entry point (CLI, MCP, or Agent) checks if a mod is disabled *before* dispatching to it. An `agon /team-tribunal` call with `--team=true` and `mod-team-tribunal` disabled will hit `Unknown command` without a clear error that suggests “re-enable mod via `/config user-toggleable-mods += mod-team-tribunal`” or a link to rollback instructions. The CLI does not emit `AGON_ROLLBACK_URL` or reference a `docs/specs/evidence/modular-agon-current-inventory.json` status.

**Defect #10: Lifecycle disposal is tied to commit state, but runtime state is not.**
CONCRETE — In `registry.ts`, the `entry.committedDispose` stores the returned `Dispose` callback, but there is no binding to `ModRegistry`’s *own* lifecycle. If `ModRegistry#close()` is called (e.g., CLI exit), pending disposers in `ownedDisposers` run, but if a mod was *disabled* mid-session, its `staged` entry is not part of `ownedDisposers`, and its `committedDispose` never runs—even though `close()` expects cleanup for *all* active registrations. This leak persists across sessions (e.g., file descriptors, registries), because ` agon --help` reuses the same `mod-kernel` singleton in-process.
