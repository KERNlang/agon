### What Actually Breaks

* **Partial Commit** – After a crash in `CandidateProcess.run()`, surface manifests may be updated before all artifacts are copied, leaving `packages/mod-kernel/src/index.ts` pointing at files that are missing, causing runtime failures (`ModuleNotFoundError`).
* **Stale Locks** – A lockfile left by an interrupted update causes subsequent CLI runs to block, even though the update had not yet finished. This manifests as an “update still in progress” error that never clears.
* **Cache Drift** – `support-persistence/cache/entrypoints.json` contains a hash for `@agon/mod-ask@1.2.3`, but the actual `dist/` file has been overwritten by a newer version. The runtime loads the old cache, causing `typeMismatch` errors.

### Edge‑Case Scenarios

* **Interrupted `npm install`** – If the user pulls a new commit that changes the `package-lock.json` during an ongoing `npm install`, the current process will try to write to a partially‑locked `node_modules`, potentially corrupting the lockfile.
* **Concurrent CI Jobs** – Two CI jobs run `npm run update` in parallel; because the temp‑dir is created without unique tokens and there is no global mutex, both jobs write into the same temp root, racing each other and corrupting the update artifacts.
* **Malicious `package.json`** – A dependency contains `scripts.postinstall` that deletes important system files. The `update` command runs `npm install` without disabling scripts, allowing this payload to execute.

### Maintenance Burden

Every new mod requires a hand‑crafted build & update script. The `candidate-process.ts` code is monolithic; adding a new type of surface (e.g., a custom engine) would require touching four different files (`update.ts`, `candidate-process.ts`, `index.ts`, and a new persistence module). The lack of an internal DSL for declaring surface dependencies makes code comprehension and future refactoring difficult.

### Incorrect Assumptions

1. **Atomicity via sequencing** – The commit sequence (`install → qualify → commit`) is assumed atomic, but the process uses multiple separate file system writes without a rollback mechanism.
2. **Integrity through npm alone** – The code trusts that `npm pack` and `npm install` are sufficient to guard against tampering. However, the code bypasses npm’s integrity checks after unpacking tarballs.
3. **Short‑lived temp files** – The design assumes that a process crash will leave no stray temp files. In reality, temp directories persist until the next run.

### MissingRequirements

| Area | Missing Feature | Why It Matters |
|------|-----------------|----------------|
| Transaction Log | Persistent journal of pre‑image hashes | Enables real rollback if a failure occurs mid‑transaction |
| Locking | Global `agon-lock` file with process ID and timestamp | Prevents concurrent updates corrupting shared state |
| Integrity Verification | SHA‑256 checksum comparison after `npm pack` extraction | Guards against malicious tarball modifications |
| Cache Validation | Runtime check of `cache/entrypoints.json` against `dist/*` before publish | Avoids stale cache drift |
| Robust Error Handling | `finally` blocks that always clean temp dir & locks | Prevents stale lockfile/dir scenario |
| Retry & Idempotence | Built‑in retry on network failures for npm install | Improves CI resilience |
| Platform Abstraction | `path.join()` for Windows | Avoids path separator bugs |

### Bottom Line

The staged **Slice 7** implementation is a *simulation* of transactional behavior.  The code base shows multiple serious weaknesses that can lead to inconsistent module states, stale locks, and even privilege escalation.  The absence of proper locking, checksums, and rollback logs makes the system *non‑transactional* in every realistic failure scenario.  Until the missing features above are addressed, the merge of Slice 7 should be blocked.
