## 1. Critical Risks (Must Address Before Proceeding)

**B1 — Cross-dispatch abort channel.** This is the single strongest blocker. The defender's own evidence — "original host signal object identity is asserted in a regression test" — is the vulnerability. The test passes *because* identity is preserved; that preservation is what makes one engine's `.abort()` cancel the host and every concurrent dispatch sharing that signal. In Agon's actual usage (parallel tribunal rounds, parallel forge candidates, brainstorm re-rounds), this is a single point of workflow-level failure triggered by the simplest possible misuse inside any forked engine. Until the signal is wrapped per-dispatch and the identity test is rewritten, "bounded dispatch" is a stated-but-not-achieved property. The attacker's negative test (one engine aborts, sibling dispatches see `aborted=true`) is concrete, runs against current code, and will fail today.

**B2 — Snapshot TOCTOU.** The trust anchor fails if pre-copy verification and post-copy verification both read from a swappable canonical path. An actor with local write — a backup tool, a peer mod in the same workspace, a file watcher retrying a half-written file — can race the copy and produce an "approved" snapshot that contains different bytes than what was actually approved. This is not a sandboxing argument; it is a classic copy-time integrity gap that any reviewer can name the fix for (`fs.open` + copy-from-FD + inode stamp). The attacker's negative test (swap between verify and copy) is constructible today and fails today. Both B1 and B2 must close before promotion from `canary` to `default`.

## 3. Accepted Risks (Acknowledged but Acceptable)

**T1 (consent-not-sandbox), T2 (subprocess hygiene), T3 (pattern redaction), T4 (snapshot retention undefined), T5 (cooperative-abort CPU window)** — all explicit trust-model limitations stated by the subject and accepted by both the defender and the attacker. None of these contradicts a stated claim. They belong in `docs/specs/modular-agon-slice8-implementation.md` under a clearly labeled "Threat Model & Out-of-Scope" section so mod authors and integrators cannot misread the contract.

**B3, B4, B5** are real but lower-severity than B1/B2. They should each have an owning issue and target slice, and must be closed before the affected surfaces are promoted from `canary` to `default` in the dispatch config. Specifically:
- **B3** blocks promotion of any host service that participates in the transactional state contract (i.e., effectively all of them).
- **B4** blocks promotion of any host caller that breaks early out of the forwarder (receipts, provenance, real-time UIs).
- **B5** blocks promotion of any environment that allows runtime registry mutation from non-parse paths (env overrides, CLI `--mod-id` flags, dynamic plugin loaders).

---

## 4. Overall Assessment

**Conditional Accept — Do not promote from `canary` to `default` until B1 and B2 are fixed.** The subject is otherwise a coherent, well-tested modularization: 76 trust/runtime, 12 folder, 34 adversarial, full S7 regressions, 47 structural controls, 31-step CLI E2E, public-API-only external example, full workspace build/typecheck/lint/pack, and green P95/RSS budgets are real evidence and they pin the named capabilities end to end. The trust-model framing (consent, not sandbox) is internally consistent and both sides of the debate agree on it.

What tips the verdict away from full accept is not the trust model — it is that **two of the attacker's blockers name exact code behaviors and constructible negative tests that fail on tree `c16dd344` today**. B1 is undermined by the defender's own evidence (identity preservation *is* the bug). B2 is undermined by the copy-time pattern itself (read-hash → copy → read-hash is a documented TOCTOU shape). These are not trust-model disputes; they are integrity-boundary defects that the spec claims to have closed.

B3–B5 and the defender's four suggestions (document 64-call budget + error code, surface fail-stop deadline in receipts, fuzz manifest charset, structured reason for safe mode) should land in the same release cycle as tracked work; the attacker's five suggestions (evidence.fd_inode stamping, explicit cap triple `{perWorker, perDispatch, perSession}`, CI invariant on `reg.surfaces.length === 5`, drain contract, retention policy) are sound follow-ups that strengthen the boundary without changing its posture.

**Net verdict: Accept the modularization as a coherent architectural milestone; gate promotion of any affected surface from `canary` to `default` on fixes for B1 and B2, with B3–B5 tracked and T1–T5 documented as accepted limitations.**
